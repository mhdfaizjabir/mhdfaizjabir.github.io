Why Harness

We rent everything now. Twenty dollars a month for Claude Pro, twenty more for GPT Pro, fractions of a cent per token for whatever runs in between. What we are actually renting is compute, inference, and a model sitting behind an API we do not control.

That should bother you more than it usually does. The model is a black box. If a provider swaps it for a cheaper one under the same name, you will not be told. If it gets quietly downgraded during a compute crunch, the name on your plan will not change. There are more variables in that relationship than you can see, let alone control.

So the real question is: how do you build something reliable on top of something you do not control?

The answer is a harness.

What a harness actually is

Strip away the AI framing and harness is an old, ordinary word. It is the thing that keeps a climber tethered to the mountain: stable, anchored, built so a slip does not turn into a fall. It is also what you put on a dog before a walk, not because the dog is broken, but because without it, it runs, and you spend the walk chasing it instead of enjoying it.

Swap climber and dog for agent and the analogy holds exactly. A harness does not make the model smarter. It keeps the model from wandering off, burning your token budget chasing a tangent, or failing quietly in a way you only notice once it is expensive.

Harness is reliability. It is the guarantee that what you built does what you need it to do, regardless of which model happens to be answering the call underneath it.

Two kinds of harness

People conflate these, but they solve different problems.

ML has the eval harness. It answers one question: is this model good? Benchmarks, holdout sets, scoring rubrics. An offline exercise that judges the model itself before anything ships.

AI engineering has the agent harness. It answers a harder question: does this system behave, in production, with real users, right now, no matter which model is plugged in underneath? That is a live, ongoing concern, not a one time score.

This post is about the second kind.

What an agent harness actually holds

Pull apart almost any agent and the same moving parts show up, every time.

  1. Tool registry. What the agent is allowed to call, and how each tool is described to the model.
  2. Model. The rented, swappable part. The one piece you never fully control.
  3. Context management. What the model actually sees at each step, and what gets dropped so it does not drown.
  4. Guardrails. The limits that stop a bad decision from becoming a bad outcome.
  5. Agent loop. The plan, act, observe cycle that turns one model call into a working process.
  6. Verify. The check that confirms the output is actually correct, not just fluent.

Everything else, the frameworks, the prompts, the retry logic, is detail sitting on top of those six. Get them right and it barely matters which model you are renting this month. Get them wrong, and the smartest model in the world will not save you.
